# 从提示词到工具的渐进式设计

需求与候选能力清楚后使用。结合最接近的[案例](../examples/README.md)，从实际任务路径设计专家。

## 专家如何逐层使用能力

| 层次 | 放什么 | 什么时候读取或执行 |
| --- | --- | --- |
| 专家简介和开场案例 | 服务对象、典型输入、用户能拿到什么。开场案例可直接复制试用 | 用户挑选专家时 |
| 专家提示词 | 职责、范围、交付质量、关键判断，以及什么时候加载哪项能力和何时补问 | 运行专家时 |
| Skill 的名称、简介与 `SKILL.md` | 触发条件、主 SOP、关键判断、参考文件入口 | 进入该工作流程时 |
| Skill 的参考资料与模板 | 分类和核查细则、不同业务场景的样例、确定的输出结构 | 当前步骤真正用到时 |
| 执行工具 | 原生工具、脚本、CLI 或 MCP，实现读取、转换、计算、查询或写入 | 需要实际数据或执行动作时 |

短小且每次都用的主 Skill 可设为 `always`。专题 Skill、长参考资料和少见流程按需加载，常见配置为 `on_demand`。把当前任务实际需要的部分放进上下文。

## 写专家提示词

建议包含四段。职责与服务对象、收到什么输入先做什么、各阶段使用哪些已绑定能力、什么样的结果可以交付。用可判断的条件表达。比如「活动稿每条数字附内部核查依据」「只有正式稿件确认后才准备发布」。

关键能力按场景写进提示词。比如「遇到历史活动资料缺失时，先在授权空间检索，找到原件后进入事实核对 SOP」。将大段模板、分类示例、供应商 API 参数和日常变更规则放进各自 Skill 或工具文档。

## 写 Skill 和执行工具

- **Skill** 拆成可执行步骤。每步说明输入、操作、结果、下一步的判断条件。重复出现的工作流写进 `SKILL.md`，详细规则、案例和模板放到 `references/` 或 `assets/`。只有一个轻量流程和少量规则时，一个入口文件即可。
- **脚本或 CLI** 用于输入和判断规则明确、需要稳定复现的动作，例如字段校验、精确去重、结构化转换和依据指定日期判定逾期。记录命令、参数、输出字段、退出码、文件读写范围和正常及异常样例。参考[本地工作台案例](../examples/workbench-delivery/README.md)。
- **MCP** 用于访问真实系统和执行该系统提供的动作。标明工具负责找什么、读哪里、返回什么、何时可以写。优先保留任务需要的权限。数据访问和有外部影响的操作按对应授权执行。
- **工具组合** 为同一步选一条主路径和必要的替代路径。例如文档 MCP 取资料、Skill 校验事实、模板生成初稿。文档 MCP 无权限时，用用户上传的资料继续，并将缺少的事实标出来。

## 设计 Skill 的文件树

依据业务裁切这个结构。方案至少列出 `SKILL.md` 及每个打算新增的文件解决什么问题。

```text
task-skill/
├── SKILL.md                 # 触发、主流程、判断和资源索引
├── references/              # 按业务步骤读取的规则、字段和案例
├── assets/                  # 输出模板或核对清单
└── scripts/                 # 有明确参数和结果的确定性操作
```

试着用用户的样例走一遍。从提示词选择 Skill，按 SOP 取输入，在需要时打开对应参考文件并调用工具，最后核对输出。发现某一步缺实际能力时，回到[调研](discovery.md)补齐。
