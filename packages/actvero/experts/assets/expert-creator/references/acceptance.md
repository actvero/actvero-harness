# 验收与交接

用用户提供的任务、脱敏样例或明确约定的模拟材料验证。验收记录应能回答这个专家拿到实际输入后，哪一步调用了什么，结果能否让用户继续工作。

## 验收顺序

交付 ZIP 或裸清单 JSON 时，先按[隔离导入步骤](import.md)对最终文件执行脚本。记录运行时版本、实际导入或阻塞的依赖、回读结果。直接保存专家时用目标返回的 ID 与 revision 回读。

1. **配置**。回读专家简介、提示词、开场示例、确切依赖、版本和启用状态。核对已提交的内容是否与方案一致。
2. **依赖**。查看核心 Skill 的文件是否可读取，脚本是否能按给定参数运行，MCP 是否按授权范围提供了目标能力。待授权或无法实测的项目保留实际状态。
3. **典型任务**。输入一份真实或代表性的材料。检查 Skill 在合适阶段加载，工具返回可追溯，输出格式、内容和质量符合约定。
4. **边界任务**。选择最容易出错的一个情形，例如缺少关键资料、两个来源冲突、MCP 没有权限、脚本输入无效。核对专家按计划补问、标记缺口或使用替代路径。

用保存结果中的 ID 在新会话召唤专家，核对选中的专家身份、版本和头像。用该会话的执行记录核实核心 Skill 随提示词加载或按需调用。创作者会话代答不能验证召唤。没有可用的召唤入口时，交接中将「新会话试跑」列为未执行，并给出输入与通过条件。

例如第一轮输入「把以下资料整理成活动新闻稿。报名表写 120 人，签到表写 96 人，活动主题是社区开放日。先给提纲，等我确认。」第一轮应列提纲，标出报名人数和签到人数的口径，等编辑决定。第二轮输入「确认提纲，分别写报名和签到人数，不加引语。」此时才输出成稿。记录两轮实际输出摘录及对应的专家 ID。

准备见证结果。例如新闻稿记录数字和引语出处，企业调研记录结论和引用，工作台记录操作步骤、版本、实际界面和业务数据。试跑使用模拟数据时标明证据范围。

## 给用户的交接内容

- 专家名称、使用入口、适合处理的任务。
- 提示词和 Skill 的主要职责，以及实际绑定的工具。
- 配置保存、依赖就绪和试跑的实际结果。无法试跑的能力列出所缺条件。
- 至少一条可直接复制的测试输入，附需要提供的样例和预期结果。合适时再给一条边界测试。

改进时保存一条可复现的输入、原输出和期望差异。按出错处调整，例如职责没写清就改提示词，分类步骤不稳定就改 Skill 及参考案例，工具查不出数据就核对绑定、权限或参数。用同一输入回跑确认改善。

## 把业务试跑做成下次还能重复的检查

每例保存输入或脱敏文件、运行版本、预期动作、实际工具调用和结果摘录。逐项记录「通过／失败／未执行」及依据。举例，稿件声称“已上线”时，应能在用户确认的变更原文中定位到该结论。某个工具出现在提示词里，不能作为实际调用记录。写作语气由用户用一篇满意的旧稿做对照。

改进已有专家时，在相同材料上对比旧输出与新输出。只改动受影响的提示词、Skill 或工具绑定，再跑失败输入以及一条原本成功的输入。对用户提供的修订意见，保留一条能够重现差异的测试。创建专家 Skill 自身的交接情景见[评测用例](../evals/evals.json)。
