# 工作台开发

面向首次接手 ACTVERO 工作台开发的 Agent。目标是完成用户确认的业务功能，交付经过校验的本地包，并核实目标客户端的安装与加载结果。业务布局、存储和 AI 操作方式由需求决定，模板中的清单不代表用户需求。

## 确认业务目标

先复用当前对话的明确需求。每次只问一个必要问题；名称未知时问“这个工作台想叫什么名字？”，允许暂定名。只有名称不等于业务范围已确认。缺少核心流程时，用业务语言建议一个最小流程，请用户确认或调整；不要求填写固定需求表。目标和最小流程不清楚时等待回答，不创建业务代码、界面或包文件，不构建、安装或发布。可先只读检查目录、说明和未提交更改；现有代码和目录名不是用户的业务意图。

已有工作台的修复或更新，先读取其源码和安装版本，保留包名、数据和用户修改；不重新询问已明确的需求，也不重新创建目录。需求足够且已确认后继续开发，不反复请求同一授权。

## 阅读当前接口

先完整读取相对本 Skill 目录的开发指南 `reference/guide.zh.md`，再读取构建版本与资源索引 `reference/environment.json`。这些文件由同一次构建生成；记录其中的运行时版本和包格式，另行核对目标客户端的实际版本。它们描述 ACTVERO 自有框架，不是旧 DSH 市场接口，也不是最新在线上游规范。用户要求查在线规范时实际获取并记录地址与版本，不能拿本快照代替。

引用路径以本 Skill 的资源目录为基准，不能假设当前工作目录是 Skill 或源码仓库。`reference/api/` 提供随构建复制的真实接口，按任务读取 Client 上下文、Host 提供者、显示与环境类型、专家清单；不要仅凭接口名字猜参数。指南中标为“源码仓库”的资料只在开发仓库中可读。

按指南的“开发环境与任务入口”核对源码根目录、Node、pnpm 和依赖。客户端内的 Skill 不等于独立编译器。找不到源码工具链时只说明缺少的开发环境，并询问其位置；不能把下载新仓库、修改宿主配置或安装别的运行时当作已获授权。版本不一致时指出具体能力差异和受阻步骤，不修改版本声明来绕过兼容性检查。

## 开发与验证

1. 确定业务范围、源码目录和安装目标。已有上下文能确定时不再提问。所有本地路径使用真实绝对路径，含空格时正确引用。不要求 GitHub 账号或仓库地址，纯本地包省略 `repository`。
2. 新建时运行指南中的 `create`，需要原生 AI 可从 `--template ai` 开始；已有源码直接修改。按指南的文件职责表分别改业务信息、界面、语言、资源和 Host 服务。包名是稳定身份；Host 与 Client 的标识和版本从同一份包信息读取。保留模板的宿主依赖及共享 React。
3. 先确定数据归属与最小读写流程。有持久化需求时使用宿主 `dataDirectory`，作者可选文件、SQLite、远程服务或 JSON 适配器，一个目录可组织多个业务项目。普通模板的浏览器存储只是示例，不能当作宿主管理的业务目录。资源目录、临时目录和会话工作目录各有用途；获取路径不授予模型文件权限。
4. AI 是可选能力。仅开原生 AI 用 `ai: true`，需要专属行为时增加专家或 `WorkbenchExpertBundle`，按指南显式连接 `activate`。专家沿用会话模型，不另造 Agent 引擎；作者选择业务工具、Skill、MCP、CLI 或已授权文件方式。验证声明、绑定、实际资源和必要运行环境，不能只把文件放进包就认为依赖已启用。打开工作台不等于发送消息或执行任务。
5. 先用业务语言确定首次无会话入口。业务整页与按需 AI、边对话边查看资料均可；显示建议在 Client 注册处配置，保留公共导航及用户记忆的开关。复用宿主主题、图标、按钮、菜单和会话组件，业务按自身容器宽度排版。图标在包信息中声明，预览图展示真实业务内容。
6. 只按需读取公开账户信息或已声明的模型目录能力。公开身份不是令牌，模型目录不代表图片或视频生成已经接通；不得把宿主凭据发到自定义地址或要求用户提供登录令牌。
7. 运行与业务变化相关的检查，再执行 `pack` 和 `check`。使用 `pack` 输出的实际路径、字节数和 SHA-256，不手猜文件名。这两个命令不执行完整 TypeScript 类型检查，不证明专家依赖启动、业务正常或安装生效。按指南“本地自测与故障定位”完成相应验证；记录命令、结果和未测项。

## 安装、加载与更新

只操作用户指定且能够确认身份的客户端/Profile；不把隔离开发客户端的结果算到日常客户端。先发现当前可用工具并读取参数。工具和界面都不可用时保留校验后的 `.tgz`，给出“工作台 → 我的工作台 → 导入工作台”的准确入口，说明安装尚未完成。

- 若目标提供专用本地安装工具，按实际参数调用，不捏造 `install_local_workbench`。若提供原生 `plugin_manager`，可先用 `list_bundles` 核对目标，再以 `install_bundle` 安装绝对路径的 `.tgz`；它影响当前 Profile 的全部会话，并沿用原生授权。
- 更新同名工作台保持包名不变并提高版本。使用支持版本替换的专用工具或管理页“更多 → 更新版本”，核对新旧版本。通用 `plugin_manager` 没有受审阅版本替换参数时不能承担这一步；不要用先卸载再安装规避检查，也不删除数据解决版本或依赖错误。
- 读取 `application`：`applied` 后核验界面；`restart-required` 只代表待重启；`failed`、`cancelled`、`overridden` 均不算已生效。未知结果先重新查询，不盲目重复安装。不绕过 `incompatible-version`。
- 不关闭或重启用户当前正在使用的目标应用，不用进程探测管理重启。需要重启时等本轮任务结束后请用户操作；在目标应用之外的隔离开发客户端，按已有授权采用其正常重启流程。
- 分别记录安装清单的包名/版本/状态、左侧切换入口、真实业务界面证据。用 `workbench_list` 检查已加载 Host 提供者；UI-only 包不会出现在该目录中。用 `workbench_open` 打开并读取确认结果，必要时用 `workbench_status` 查询；仅 `confirmed` 表示宿主视图已挂载，仍需验证业务内容。

## 验收与交付

按指南的自测表选择适用项：无会话首次进入、实际业务读写、重开与刷新保留、原生 AI 及声明的操作方式、不同对话隔离、显示切换与记忆、窄容器、明暗主题、更新后数据。不要为未使用的 MCP、CLI 或平台能力建立验收要求。

用户未授权模型费用或外部写入时，不为验收自动提交生成或发送任务；可以验证本地依赖和界面，将真实调用标为待验证。模型不可用时先验证本地业务，不要求给专家另配模型。

工作台问题在其源码中修复、提高版本并重建，保留已安装文件用于诊断；不直接改安装目录或同版本缓存。白屏、找不到入口、AI 失败和数据不一致分别按指南定位，不能把全部问题归为需要重启。

## 完成汇报

先说明能做什么、实际执行的操作和未验证项，再列修改文件、实际包路径和检查结果。最后以醒目的“接下来怎么用”三点收尾，之后不追加内容：① 用实际工作台名称说明开发、安装与加载状态，未完成不得宣称已安装；② 只有安装成功且需要重启时，请用户等任务结束后点击顶部“立即重启”或“Harness → 重启 Harness”，通常无需退出桌面应用，其他情况如实说明；③ 展开侧栏，在“工作台”右侧的名称切换区域选择实际工作台，未显示时到“工作台 → 我的工作台”检查安装及加载状态。用户可以直接试用，不必返回对话；需要继续验收时可回原对话说“重启好了”，Agent 再核验入口和真实界面。
